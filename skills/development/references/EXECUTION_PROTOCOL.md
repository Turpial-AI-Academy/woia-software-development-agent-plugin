# Execution Protocol

## 1. Establish implementation state

Before editing, record:

- SPEC/change identifier;
- acceptance criteria;
- task list and dependencies;
- current branch/ref/HEAD when source control exists;
- affected surfaces;
- repository commands needed for focused validation.

Use the repository's existing task/status mechanism when present. Do not create a competing project-management system merely for this capability.

## 2. Map tasks to outcomes

For each task, record which acceptance criterion or necessary enabling change it serves.

A task with no relationship to the approved change is suspect. Clarify or defer it instead of silently expanding scope.

## 3. Task lifecycle

A working task may use the repository's own statuses. Conceptually:

~~~text
OPEN -> IN_PROGRESS -> CLOSED
                    -> SKIPPED(reason)
                    -> BLOCKED(reason)
~~~

Only `CLOSED` and `SKIPPED(reason)` are terminal for the development gate.

`BLOCKED`, `OPEN`, or `IN_PROGRESS` means the gate is not satisfied.

A skip reason must be concrete, such as:

- task became unnecessary because another approved change satisfies the same acceptance criterion;
- repository evidence proves the task's assumed work already exists;
- SPEC explicitly makes the task conditional and the condition is false.

"Not needed" without evidence is not sufficient.

## 4. Implement one coherent slice at a time

For each slice:

1. inspect the current implementation and nearby conventions;
2. make the smallest authorized change;
3. update directly affected tests/config/docs/generated inputs as needed;
4. run a focused validation if useful;
5. inspect the diff for accidental scope;
6. close or explicitly skip the task only when justified.

Do not batch unrelated cleanup into the same slice.

## 5. Generated code and derived artifacts

When a repository defines a canonical generator:

- change the source-of-truth input;
- run the generator using the repository's documented workflow;
- validate generated output;
- do not hand-edit derived output unless the repository explicitly treats it as editable.

If the generator is unavailable, report the limitation. Do not fabricate generated bytes.

## 6. Migrations and compatibility

Treat database migrations, persisted formats, public APIs, schemas, events, deployment manifests, and rollback paths as compatibility-sensitive.

If a task changes one of these, inspect the repository's established migration/compatibility mechanism and keep the change within the SPEC. Escalate irreversible or materially broader consequences.

## 7. Refactoring

Refactor only when it:

- is necessary for the SPEC;
- removes duplication introduced by the implementation;
- keeps the changed area understandable/maintainable;
- preserves observable behavior outside approved acceptance criteria.

Do not use implementation work as a pretext for repository-wide cleanup or architecture restyling.

## 8. Source-head readiness

Before reporting review readiness:

- ensure the intended implementation is represented in source control according to the repository's workflow;
- identify the exact branch/ref and commit/head SHA when Git is used;
- verify the head corresponds to the implementation being reported;
- report uncommitted intended changes as **not review-ready** unless the repository explicitly defines another reviewable source-state mechanism.

Creating implementation commits may be appropriate when authorized by the repository workflow. This capability does not authorize merge, tag, publication, release, or deployment.
